# Releasing

How an oxidizr version gets out the door. The whole flow is: **prepare on
`main` → tag locally → the user pushes → CI builds and publishes → smoke →
sync the journal**. Nothing in this document is automated from a dev
machine: pushing and publishing stay explicit human actions.

Binaries are packaged and published by
[cargo-dist](https://axodotdev.github.io/cargo-dist/); its configuration is
`dist-workspace.toml` at the workspace root and the generated CI is
`.github/workflows/release.yml` (never hand-edit that file — see
[Tooling](#tooling)).

## Before the tag

1. **Gates green** (in `nix develop`):

   ```sh
   cargo xtask ci                                  # fmt + clippy + test + refs
   OXIDZR_E2E_FULL=1 cargo test -p oxidizr-e2e     # full e2e tier
   cargo xtask e2e bless                           # every line ": unchanged"
   git status --porcelain testdata/                # must be empty
   ```

   Run the oracle legs against the reference binary when the diff touches
   generator or parser code (`cargo xtask oracle verify`,
   `cargo xtask export-verify --format …`, all with `TZ=UTC`); otherwise
   record the skip with its reason.

2. **Version bump.** The version lives in exactly one place — the
   `[workspace.package]` table in the root `Cargo.toml` — plus one
   `version = "…"` pin per path dependency in `workspace.dependencies`.
   Then refresh the lockfile:

   ```sh
   cargo update --workspace
   ```

   Tests and help texts derive their version strings from
   `CARGO_PKG_VERSION`, and the JSON output carries no generator or version
   field, so a bump moves no goldens. Verify with the `--version` tests:

   ```sh
   cargo test -p oxidizr-lsp --test version
   cargo test -p oxidizr-cli -- --version
   ```

3. **CHANGELOG.md.** Cut the `## [Unreleased]` section into
   `## [X.Y.Z] - <date>` at the top (Keep-a-Changelog form:
   Added / Changed / Fixed); tidy the wording, keep the substance.
   Rust-API churn lines live in `[Unreleased]` already — waves append
   theirs the commit that makes the change (since v0.4.0 there is no
   separate running list).

4. **Docs pass.** The README command table matches `oxidizr --help`;
   `docs/*.md` schemas are current.

5. **Commit** the release chore on `main`.

## Tag

Annotated tag on the release commit, message summarising the phase:

```sh
git tag -a v0.4.0 -m "Phase 4 complete: …"
```

The tag is LOCAL until the user decides otherwise — never push it from a
work session.

## Publish (user action)

Pushing the tag is the release trigger:

```sh
git push origin main
git push origin v0.4.0
```

`.github/workflows/release.yml` (generated by cargo-dist) then builds each
release app — `oxidizr` (from `oxidizr-cli`), `oxidizr-lsp`,
`oxidizr-viewer` (built with `--features gui`) — for the five targets in
`dist-workspace.toml`, computes SHA-256 checksums, generates the shell and
PowerShell installers, and creates the GitHub Release.

## Smoke

`.github/workflows/release-smoke.yml` runs automatically once the release
is published (it can also be dispatched manually with a tag input). Per OS
it downloads the release assets, verifies the checksums, checks each
binary's `--version` against the tag, and converts one test workspace with
`oxidizr dsl2json`. The GUI binary is checksum- and archive-verified only;
a headless runner cannot verify a window.

## crates.io

Publishing to crates.io is **skipped as of v0.4.0** (user decision,
2026-11-22): the release ships binaries and installers via the GitHub
Release only. The library crates keep `publish = true` as a statement of
intent; the CLI crate stays `publish = false` (its binary ships through
cargo-dist's `dist = true` override). If registry publishing is taken up
later, publish bottom-up along the dependency chain
(`oxidizr-core` → … → `oxidizr-api`) and re-check the generated publish
jobs afterwards.

## After the release

- Record the tag in the journal: `agents/plan/PROGRESS.md` status-board row
  and milestone log.
- Update the session checkpoint `agents/notes/RESUME.md`.

## Tooling

- `dist` comes from the Nix dev shell (`nix develop --command dist plan`).
- After changing `dist-workspace.toml` or a `[package.metadata.dist]`
  table, regenerate the CI workflow and keep it pure:

  ```sh
  nix develop --command dist generate --mode ci
  nix develop --command dist plan       # validates config + workflow
  ```

- The workflow files are linted by `cargo xtask lint` (actionlint); the
  generated `release.yml` has narrowly scoped shellcheck exceptions in
  `.github/actionlint.yaml`.
- Why the config sits in `dist-workspace.toml` (and not
  `[workspace.metadata.dist]`): see
  `agents/notes/pitfalls/cargo-dist-installer-panic.md`.
